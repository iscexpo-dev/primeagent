Primeagent stores application data such as flows, users, and API keys in a SQL database.

When you upgrade Primeagent or connect to a new empty database, Primeagent must keep the database schema aligned with the application models.

By default, the Primeagent database uses [SQLite](https://www.sqlite.org/docs.html), and uses [Alembic](https://alembic.sqlalchemy.org/) for SQL database migrations.

This page explains when migrations run and how to run and repair migrations safely.

To move users, flows, files, and knowledge bases to another Primeagent installation, see [Move to a new Primeagent instance](/instance-migration).

## Default migrations behavior and triggers

Most Primeagent users never need to run a database migration.
When you start Primeagent, or restart a container after upgrading the Primeagent image, pending Alembic migrations run as part of database initialization.

Primeagent includes [Alembic revision scripts](https://github.com/khulnasoft-bot/primeagent/tree/main/src/backend/base/primeagent/alembic) with the package.
On startup, Primeagent connects to the database at [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) or the default `primeagent.db` file, ensures the required tables exist, checks the database schema against the current models, and then applies any pending Alembic upgrades to bring the schema to its `head` revision.

Alembic records the applied revision in the `alembic_version` table.

Other events that trigger Alembic checks are a first Primeagent startup against a new SQLite file or empty PostgreSQL database, upgrading to a Primeagent version that includes new Alembic revisions, or pointing [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) at an empty database.

## Upgrade Primeagent safely

To upgrade Primeagent or change the database URL in a deployment that already has data, you may need a database migration.
To migrate your database, do the following:

1. Stop Primeagent.
2. Back up the database.

    If you're using SQLite, copy the `primeagent.db` file.
    The default path depends on your install method and whether `PRIMEAGENT_SAVE_DB_IN_CONFIG_DIR` is set.
    For more information, see [Memory management options](/memory#storage-options-and-paths).

    If you're using PostgreSQL, make a logical backup with `pg_dump`, or use your database provider's snapshot.
    For more information, see [enterprise backup guidance](/enterprise-database-guide).

3. Export any flows you want to save as JSON. For more information, see [Import and export flows](/concepts-flows-import).
4. Upgrade the Primeagent package or container image to the latest version, keeping the same [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) or the same SQLite path.

    ```bash
    uv pip install primeagent -U
    ```

5. Start a **single** Primeagent instance, so database migrations run without concurrent database writes.
6. Confirm that startup succeeds.
7. If startup reports a schema mismatch, run `primeagent migration` to inspect the problem and restore from backup if needed.
   For more information, see [`primeagent migration` CLI](/configuration-cli#primeagent-migration).

## UTC timestamps in Primeagent 1.13

Primeagent 1.13 adopts SQLModel's UTC datetime storage for previously inferred datetime fields.
PostgreSQL converts 19 timestamp columns across users, API keys, files, flows, MCP servers, SSO user profiles, messages, transactions, vertex builds, traces, and spans to `TIMESTAMP WITH TIME ZONE`.
The migration interprets existing values as UTC, matching Primeagent's timestamp writers, and preserves microseconds and null values independently of the PostgreSQL session timezone.
If another application wrote local times directly to these columns, reconcile those values before upgrading: their original timezone cannot be recovered from the stored timestamps.

Follow the upgrade procedure above with all old backend instances, workers, and listeners stopped.
Start one upgraded backend to run the migration before starting the remaining upgraded processes.
This change does not support mixing older and newer application versions against the same database: older schema checks expect timestamps without timezone information.
PostgreSQL takes exclusive locks on the affected tables and may rewrite their data and indexes, so allow a maintenance window sized for the message and tracing tables.

SQLite needs no timestamp schema conversion; SQLModel now restores UTC timezone information when reading historical timestamps.
Legacy flow and message timestamps and trace filters without an offset continue to be interpreted as UTC.
Custom code that writes directly through SQLModel must supply aware timestamps, such as `datetime.now(timezone.utc)`; naive datetime parameters are rejected by the new SQLModel type.
Datetime fields returned by the ORM are now aware, and API fields without a custom serializer include a UTC offset.

To reverse this timestamp conversion, stop all upgraded processes and use the 1.13 migration code to downgrade revision `f2a7c9e4b681` to its parent `9d7e2a6c4b81`.
The downgrade converts the affected PostgreSQL values back to naive UTC, preserving the represented instants.
This reverses only the timestamp change. Before starting an older release, follow the rollback procedures for any other intervening migrations; restoring the pre-upgrade backup is the fallback.

## Switch from SQLite to PostgreSQL

Changing `PRIMEAGENT_DATABASE_URL` from SQLite to PostgreSQL does **not** copy existing SQLite data into PostgreSQL.
Primeagent initializes and migrates the new database schema, and your previous SQLite file remains where it was.

To copy everything from SQLite into PostgreSQL, stop Primeagent and run `primeagent convert-sqlite-to-postgres`:

```bash
primeagent convert-sqlite-to-postgres \
  --source sqlite:////path/to/primeagent.db \
  --target postgresql://user:password@host:5432/primeagent
```

A command line is visible to other users of the machine, so to keep the PostgreSQL password out of it, set `PRIMEAGENT_MIGRATION_SOURCE_URL` and `PRIMEAGENT_MIGRATION_TARGET_URL` instead of passing `--source` and `--target`.
If both are given, the options win.

The SQLite database must already be on the schema of the Primeagent version you run the command with, so start that version against it once first.
If you copy the SQLite file before converting, use `sqlite3 primeagent.db ".backup copy.db"` or `VACUUM INTO`. Primeagent runs SQLite in WAL mode, so a plain file copy can come out empty.

The command creates the PostgreSQL schema, copies every row in one transaction, and checks each table's row count before committing.
If anything is refused, such as a value PostgreSQL does not accept or a target database that already belongs to another instance, nothing is written and the command lists the problems.

SQLite never enforced Primeagent's foreign keys, so deleting a user or clearing a flow's traces can leave rows that point at a deleted row.
PostgreSQL rejects those rows, so the command refuses them by default and lists each table, column, and row count.
To copy without them, rerun with `--drop-orphans`. Rows that PostgreSQL would have deleted along with their parent (`ON DELETE CASCADE`) are left out, keys it would have cleared (`ON DELETE SET NULL`) are set to `NULL`, and the command reports how many rows it handled for each.
Keep the same `PRIMEAGENT_SECRET_KEY` when you point Primeagent at the new database, or stored credentials can't be decrypted.

To run the command from another program, add `--json`.
It then writes one JSON object per line to standard output: `progress` as it checks the source, prepares the target, and copies rows, `item` for each copied table, `error` or `decision_needed` for anything it refuses, and a final `report`.
Each problem carries a stable `code`, logs go to standard error, and the exit code is non-zero if anything was refused or failed.
A run stopped by `SIGINT` or `SIGTERM` ends with an `error` whose `code` is `interrupted`, and exits with 130 for `SIGINT` or 143 for `SIGTERM`.

To move only your flows instead, do the following:

1. [Export flows](/concepts-flows-import), and note any [global variables](/configuration-global-variables) or credentials.
2. Provision PostgreSQL 15+ and set `PRIMEAGENT_DATABASE_URL` as described in [Configure an external PostgreSQL database](/configuration-custom-database).
3. If required, install PostgreSQL driver extras, for example `uv pip install "primeagent[postgresql]"`.
4. Start Primeagent. The new PostgreSQL schema is created.
5. Import the exported flows and recreate secrets or variables as needed.

## Migration logging

Alembic output is written to a log file by default at `alembic/alembic.log` under the Primeagent config directory (`PRIMEAGENT_CONFIG_DIR`).
Relative `PRIMEAGENT_ALEMBIC_LOG_FILE` values are also resolved against that config directory.
In read-only or hardened containers, that path may not be writable, and Primeagent will fall back to `stdout` and continue the migration.

## Migration environment variables

| Variable | Purpose |
|----------|---------|
| `PRIMEAGENT_ALEMBIC_LOG_TO_STDOUT` | Set to `true` to send Alembic migration output to `stdout`. |
| `PRIMEAGENT_ALEMBIC_LOG_FILE` | Absolute or relative path for the Alembic log file when not logging to `stdout`. Relative paths resolve under the Primeagent config directory. |
| `PRIMEAGENT_MIGRATION_LOCK_TIMEOUT_S` | Seconds to wait for the PostgreSQL migration advisory lock. Default: `300`. |
| `PRIMEAGENT_MIGRATION_LOCK_NAMESPACE` | Optional namespace for the Alembic PostgreSQL advisory lock. The default lock key coordinates instances that share a database. Set this variable to isolate different Primeagent deployments that share one PostgreSQL server. Use the same value on every instance in that deployment. |
