This page documents Primeagent's built-in authentication, including user accounts, Primeagent API keys, and the environment variables that control access to your server.
To connect Primeagent to an external identity provider or SSO system, see [SSO and external authentication](./external-authentication).

:::warning
Never expose Primeagent ports directly to the internet without proper security measures.
Set `PRIMEAGENT_AUTO_LOGIN=False`, use a non-default `PRIMEAGENT_SECRET_KEY`, and deploy your Primeagent server behind a reverse proxy with authentication enabled.
For more information, see [Start a Primeagent server with authentication enabled](#start-a-primeagent-server-with-authentication-enabled).
:::

Authentication credentials help prevent unauthorized access to your Primeagent server, flows, and services connected through components.

There are three types of credentials that you use in Primeagent:

* [Primeagent API keys](#primeagent-api-keys): For authentication with the Primeagent API and authorizing server-side Primeagent actions like running flows and uploading files.
* [Component API keys](#component-api-keys): For authentication between Primeagent and a service connected through a component, such as a model provider or third-party API.
* [Authentication environment variables](#authentication-environment-variables): These environment variables configure how Primeagent handles user authentication and authorization.

## Primeagent API keys {#primeagent-api-keys}

You can use Primeagent API keys to interact with Primeagent programmatically.

By default, most Primeagent API endpoints, such as `/v1/run/$FLOW_ID`, require authentication with a Primeagent API key.

Primeagent validates API keys against keys stored in the database, but you can configure Primeagent to validate API keys against an environment variable instead.
For more information, see [`PRIMEAGENT_API_KEY_SOURCE`](#primeagent-api-key-source).

Webhook endpoints require API key authentication by default. To disable authentication for webhook endpoints, use the [`PRIMEAGENT_WEBHOOK_AUTH_ENABLE`](/webhook#require-authentication-for-webhooks) environment variable.
To configure authentication for Primeagent MCP servers, see [Use Primeagent as an MCP server](/mcp-server).

### Primeagent API key permissions

A Primeagent API key adopts the privileges of the user who created it.
This means that API keys you create have the same permissions and access that you do, including access to your flows, components, and Primeagent database.
A Primeagent API key cannot be used to access resources outside of your own Primeagent server.

In single-user environments, you are always a superuser, and your Primeagent API keys always have superuser privileges.

In multi-user environments, users who aren't superusers cannot use their API keys to access other users' resources.
Superusers can only run their own flows, and cannot run flows owned by other users.
You must [start your Primeagent server with authentication enabled](#start-a-primeagent-server-with-authentication-enabled) to allow superusers to manage users and create non-superuser accounts.

### Create a Primeagent API key

You can generate a Primeagent API key in your Primeagent **Settings** or with the Primeagent CLI.

The CLI option is required if your Primeagent server is running in `--backend-only` mode.

<Tabs>
<TabItem value="settings" label="Primeagent Settings" default>

1. In the Primeagent header, click your profile icon, and then select **Settings**.
2. Click **Primeagent API Keys**, and then click **Add New**.
3. Name your key, and then click **Create API Key**.
4. Copy the API key and store it securely.

</TabItem>
<TabItem value="Primeagent CLI" label="Primeagent CLI">

If you're serving your flow with `--backend-only=true`, you can't create API keys in your Primeagent **Settings** because the frontend isn't running.
In this case, you must create API keys with the Primeagent CLI.

1. Recommended: [Start your Primeagent server with authentication enabled](#start-a-primeagent-server-with-authentication-enabled).

    The Primeagent team recommends enabling authentication for security reasons to prevent unauthorized creation of API keys and superusers, especially in production environments.
    If authentication isn't enabled (`PRIMEAGENT_AUTO_LOGIN=True`), all users are effectively superusers, and they can create API keys with the Primeagent CLI.

2. Create an API key with [`primeagent api-key`](/configuration-cli#primeagent-api-key):

    ```shell
    uv run primeagent api-key
    ```

    All API keys created with the Primeagent CLI have superuser privileges because the command requires superuser authentication, and Primeagent API keys adopt the privileges of the user who created them.

</TabItem>
</Tabs>

### Use a Primeagent API key

To authenticate Primeagent API requests, pass your Primeagent API key an `x-api-key` header or query parameter.

<Tabs>
<TabItem value="header" label="HTTP header" default>

```shell
curl -X POST \
  "http://$PRIMEAGENT_SERVER_ADDRESS/api/v1/run/$FLOW_ID?stream=false" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $PRIMEAGENT_API_KEY" \
  -d '{"inputs": {"text":""}, "tweaks": {}}'
```

</TabItem>
<TabItem value="parameter" label="Query parameter">

```shell
curl -X POST \
  "http://$PRIMEAGENT_SERVER_ADDRESS/api/v1/run/$FLOW_ID?x-api-key=$PRIMEAGENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"inputs": {"text":""}, "tweaks": {}}'
```

</TabItem>
</Tabs>

For more information about forming Primeagent API requests, see [Get started with the Primeagent API](/api-reference-api-examples) and [Trigger flows with the Primeagent API](/concepts-publish).

### Track API key usage

By default, Primeagent tracks API key usage through `total_uses` and `last_used_at` records in your [Primeagent database](/memory).

To disable API key tracking, set `PRIMEAGENT_DISABLE_TRACK_APIKEY_USAGE=True` in your [Primeagent environment variables](/environment-variables).
This can help avoid database contention during periods of high concurrency.

### Revoke an API key

To revoke and delete an API key, do the following:

1. In the Primeagent header, click your profile icon, and then select **Settings**.
2. Click **Primeagent API Keys**.
3. Select the keys you want to delete, and then click <Icon name="Trash2" aria-hidden="true"/> **Delete**.

This action immediately invalidates the key and prevents it from being used again.

## Component API keys {#component-api-keys}

Component API keys authorize access to external services that are called by components in your flows, such as model providers, databases, or third-party APIs.
These aren't Primeagent API keys or general application credentials.

In Primeagent, you can store component API keys in global variables in your **Settings** or import them from your runtime environment.
For more information, see [Global variables](/configuration-global-variables).

You create and manage component API keys within the service provider's platform.
Primeagent only stores the encrypted key value or a secure reference to a key stored elsewhere; it doesn't manage the actual credentials at the source.
This means that deleting a global variable from Primeagent doesn't delete or invalidate the actual API key in the service provider's system.
You must delete or rotate component API keys directly using the service provider's interface or API.

For added security, you can set `PRIMEAGENT_REMOVE_API_KEYS=True` to omit API keys and tokens from flow data in your [Primeagent database](/memory).
Additionally, when [exporting flows](/concepts-flows-import), you can choose to omit API keys from the exported flow JSON.

## Authentication environment variables

This section describes the available authentication configuration variables.

You can use the [`.env.example`](https://github.com/khulnasoft-bot/primeagent/blob/main/.env.example) file in the Primeagent repository as a template for your own `.env` file.

For JWT token signing configuration, including algorithm selection and key management, see [Configure JWT token signing](#configure-jwt-token-signing).

### PRIMEAGENT_AUTO_LOGIN {#primeagent-auto-login}

This variable controls whether the visual editor uses automatic login or requires users to sign in.

* If `PRIMEAGENT_AUTO_LOGIN=False`, automatic login is disabled. Users must sign in to the visual editor, authenticate as a superuser to run certain Primeagent CLI commands, and use a Primeagent API key for Primeagent API requests.
You must explicitly set [`PRIMEAGENT_SUPERUSER_PASSWORD`](#primeagent-superuser) before startup. Set [`PRIMEAGENT_SUPERUSER`](#primeagent-superuser) only if you want to override the default superuser username (`primeagent`).

* If `PRIMEAGENT_AUTO_LOGIN=True`, the visual editor automatically signs in all users as the configured superuser, and Primeagent uses that username with a configured or generated bootstrap password.
All users share the same visual editor environment without password protection, and they can run Primeagent CLI commands as superusers.
API requests still require a Primeagent API key unless you also set [`PRIMEAGENT_SKIP_AUTH_AUTO_LOGIN`](#primeagent-skip-auth-auto-login) to `true`.

The Primeagent application default is `True`.
Official Primeagent Docker images set `false`. For more information, see [Docker image defaults](/deployment-docker#docker-image-security-defaults).

#### PRIMEAGENT_SKIP_AUTH_AUTO_LOGIN {#primeagent-skip-auth-auto-login}

When `PRIMEAGENT_AUTO_LOGIN=true`, set `PRIMEAGENT_SKIP_AUTH_AUTO_LOGIN=true` to also skip API key authentication for API requests.
The default is `false`, so API keys are still required even when auto-login is enabled.
This variable will be removed in a future release.

### PRIMEAGENT_ENABLE_SUPERUSER_CLI {#primeagent-enable-superuser-cli}

Controls the availability of the `primeagent superuser` command in the Primeagent CLI.
The default is `true`, but `false` is recommended to prevent unrestricted superuser creation.
For more information, see [`primeagent superuser`](/configuration-cli#primeagent-superuser).

### PRIMEAGENT_SUPERUSER and PRIMEAGENT_SUPERUSER_PASSWORD {#primeagent-superuser}

These variables specify the username and password for the Primeagent server's superuser.

```text
PRIMEAGENT_SUPERUSER=administrator
PRIMEAGENT_SUPERUSER_PASSWORD=securepassword
```

`PRIMEAGENT_SUPERUSER_PASSWORD` is required if `PRIMEAGENT_AUTO_LOGIN=False`. `PRIMEAGENT_SUPERUSER` is optional and defaults to `primeagent`.
`PRIMEAGENT_SUPERUSER_PASSWORD` can't use the legacy default value `primeagent`; startup fails closed instead.
When `PRIMEAGENT_AUTO_LOGIN=True`, `PRIMEAGENT_SUPERUSER` selects the auto-login account username and `PRIMEAGENT_SUPERUSER_PASSWORD` is optional. If the password isn't set, Primeagent generates an unknown bootstrap password for the auto-login account.

When you [start a Primeagent server with authentication enabled](#start-a-primeagent-server-with-authentication-enabled), if the required password is _not_ set, then startup fails instead of creating a default password.
These defaults don't apply when using the Primeagent CLI command [`primeagent superuser`](/configuration-cli#primeagent-superuser).

### PRIMEAGENT_SECRET_KEY {#primeagent-secret-key}

This environment variable stores a secret key used for encrypting sensitive data like API keys and for JWT signing when using the HS256 algorithm.
Primeagent uses the [Fernet](https://pypi.org/project/cryptography/) library for secret key encryption.
For JWT-specific configuration, see [Configure JWT token signing](#configure-jwt-token-signing).

If no secret key is provided, Primeagent automatically generates one.

However, you should generate and explicitly set your own key in production environments.
This is particularly important for multi-instance deployments like Kubernetes to ensure consistent encryption across instances.

To generate a secret encryption key for `PRIMEAGENT_SECRET_KEY`, do the following:

1. Run the command to generate and copy a secret to the clipboard.

    <Tabs>
    <TabItem value="unix" label="macOS or Linux">

    * **macOS**: Generate a secret key and copy it to the clipboard:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'PRIMEAGENT_SECRET_KEY={token_urlsafe(32)}')" | pbcopy
        ```

    * **Linux**: Generate a secret key and copy it to the clipboard:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'PRIMEAGENT_SECRET_KEY={token_urlsafe(32)}')" | xclip -selection clipboard
        ```

    * **Unix**: Generate a secret key and print it to the terminal to manually copy it:

        ```bash
        python3 -c "from secrets import token_urlsafe; print(f'PRIMEAGENT_SECRET_KEY={token_urlsafe(32)}')"
        ```

    </TabItem>
    <TabItem value="windows" label="Windows">

    * Generate a secret key and copy it to the clipboard:

        ```bash
        python -c "from secrets import token_urlsafe; print(f'PRIMEAGENT_SECRET_KEY={token_urlsafe(32)}')"
        ```

    * Generate a secret key and print it to the terminal to manually copy it:

        ```bash

        # Or just print
        python -c "from secrets import token_urlsafe; print(f'PRIMEAGENT_SECRET_KEY={token_urlsafe(32)}')"
        ```

    </TabItem>
    </Tabs>

2. Paste the value into your `.env` file:

    ```text
    PRIMEAGENT_SECRET_KEY=dBuu...2kM2_fb
    ```

    If you're running Primeagent on Docker, reference the `PRIMEAGENT_SECRET_KEY` from your `.env` file in the `docker-compose.yml` file like this:

        ```yaml
        environment:
          - PRIMEAGENT_SECRET_KEY=${PRIMEAGENT_SECRET_KEY}
        ```

#### Rotate the secret key {#rotating-the-secret-key}

Rotate `PRIMEAGENT_SECRET_KEY` if the key might have been compromised and as part of your routine credential management practices.
Primeagent provides a migration script that re-encrypts stored credentials and other sensitive data with a new key so you can rotate without losing access.

For more information, see [Secret Key Rotation](https://github.com/khulnasoft-bot/primeagent/blob/main/SECURITY.md#secret-key-rotation) in the Primeagent Security Policy.

### PRIMEAGENT_NEW_USER_IS_ACTIVE {#primeagent-new-user-is-active}

When `PRIMEAGENT_NEW_USER_IS_ACTIVE=False` (default), new accounts are inactive until a superuser activates them with the [Users API](/api-users).
Inactive users cannot sign in to the visual editor.
The superuser can also deactivate an account with the same API.

When `PRIMEAGENT_NEW_USER_IS_ACTIVE=True`, new accounts are automatically activated.

```text
PRIMEAGENT_NEW_USER_IS_ACTIVE=False
```

Only superusers can manage user accounts for a Primeagent server through the [Users API](/api-users).
For more information, see [Start a Primeagent server with authentication enabled](#start-a-primeagent-server-with-authentication-enabled).

### PRIMEAGENT_ENABLE_SIGNUP {#primeagent-enable-signup}

This variable controls whether public self-registration is allowed at the `POST /api/v1/users/` endpoint.

| Value | Description |
|-------|-------------|
| `True` (default) | Anyone can create a new Primeagent account by calling the registration endpoint directly. |
| `False` | Public registration is disabled. Only superusers can create new accounts with the [Users API](/api-users). |

Self-registration is always disabled when `PRIMEAGENT_AUTO_LOGIN=True`, because single-user mode has no multi-account concept.
Superusers can create accounts regardless of this setting.

### PRIMEAGENT_API_KEY_SOURCE {#primeagent-api-key-source}

This variable controls how Primeagent validates API keys.

| Value | Description |
|-------|-------------|
| `db` (default) | Validates API keys against [Primeagent API keys](#primeagent-api-keys) stored in the database. This is the standard behavior where users create and manage API keys through the Primeagent UI or CLI. |
| `env` | Validates API keys against the `PRIMEAGENT_API_KEY` environment variable. Useful for Kubernetes deployments, CI/CD pipelines, or any environment where you want to inject a pre-defined API key without database configuration. |

By default, Primeagent validates the `x-api-key` header against the Primeagent database with `PRIMEAGENT_API_KEY_SOURCE=db`.
When using database-based validation, you can create multiple keys with per-user permissions, track usage, and manage keys through the Primeagent UI or CLI.

When `PRIMEAGENT_API_KEY_SOURCE=env`, Primeagent validates the `x-api-key` header against the value of the `PRIMEAGENT_API_KEY` environment variable.
This means Primeagent runs securely in stateless environments, such as with WFX or Kubernetes secrets.

When `PRIMEAGENT_API_KEY_SOURCE=env`, only a single API key can be used for the deployment. All authenticated requests use the same API key, and successful authentication grants superuser privileges.
This mode is designed for single-tenant deployments or automated systems, not multi-user environments where different users need different access levels. To rotate your keys, update the environment variable and restart the Primeagent server.

To enable environment-based API key validation:

1. In the Primeagent `.env` file, set the API key source to `env`:

    ```text
    PRIMEAGENT_API_KEY_SOURCE=env
    ```

2. In the Primeagent `.env` file, set the API key value:

    ```text
    PRIMEAGENT_API_KEY=your-secure-api-key
    ```

3. Use the API key in your requests:

    ```shell
    curl -X POST \
      "http://PRIMEAGENT_SERVER_ADDRESS/api/v1/run/FLOW_ID?stream=false" \
      -H "Content-Type: application/json" \
      -H "x-api-key: PRIMEAGENT_API_KEY" \
      -d '{"inputs": {"text":""}, "tweaks": {}}'
    ```

    Replace `PRIMEAGENT_SERVER_ADDRESS`, `FLOW_ID`, and `PRIMEAGENT_API_KEY` with the values from your deployment.

<details>
<summary>Kubernetes deployment example</summary>

To configure an environment-based API key in a Kubernetes Secret, do the following:

1. Create a Kubernetes Secret with your API key:

    ```yaml
    apiVersion: v1
    kind: Secret

      name: primeagent-api-key
    type: Opaque
    ```


</details>

### PRIMEAGENT_CORS_* {#cors-configuration-for-authentication}

Cross-Origin Resource Sharing (CORS) configuration controls how authentication credentials are handled when your Primeagent frontend and backend are served from different origins.
The following `PRIMEAGENT_CORS_*` environment variables are available:

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_CORS_ALLOW_CREDENTIALS` | Boolean | `True` | Whether to allow credentials, such as cookies and authorization headers, in CORS requests. |
| `PRIMEAGENT_CORS_ALLOW_HEADERS` | List[String] or String | `*` | The allowed headers for CORS requests. Provide a comma-separated list of headers or use `*` to allow all headers. |
| `PRIMEAGENT_CORS_ALLOW_METHODS` | List[String] or String | `*` | The allowed HTTP methods for CORS requests. Provide a comma-separated list of methods or use `*` to allow all methods. |
| `PRIMEAGENT_CORS_ORIGINS` | String | `*` | The allowed CORS origins. Provide a comma-separated list of origins or use `*` for all origins. |

The default configuration enables CORS credentials and uses wildcards (`*`) to allow all origins, headers, and methods:

```text
PRIMEAGENT_CORS_ORIGINS=*
PRIMEAGENT_CORS_ALLOW_CREDENTIALS=True
PRIMEAGENT_CORS_ALLOW_HEADERS=*
PRIMEAGENT_CORS_ALLOW_METHODS=*
```

:::danger
Primeagent's default CORS settings can be a security risk in production environments because any website can make requests to your Primeagent API, and any website can include credentials in cross-origin requests, including authentication cookies and authorization headers.

In production deployments, specify exact origins in `PRIMEAGENT_CORS_ORIGINS`.
You can also specify allowed headers and methods, if needed.
For example:

```text
PRIMEAGENT_CORS_ORIGINS=["https://yourdomain.com","https://app.yourdomain.com"]
PRIMEAGENT_CORS_ALLOW_CREDENTIALS=True
PRIMEAGENT_CORS_ALLOW_HEADERS=["Content-Type","Authorization"]
PRIMEAGENT_CORS_ALLOW_METHODS=["GET","POST","PUT"]
```
:::

### PRIMEAGENT_ACCESS_* and PRIMEAGENT_REFRESH_* {#session-cookie-hardening}

For a shared or public deployment served over HTTPS, harden the session cookies.
`Secure` and `SameSite` default to values that support local HTTP development.
Both the access and refresh cookies are `HttpOnly` by default; the browser sends them automatically with requests.

Set both `PRIMEAGENT_ACCESS_SECURE` and `PRIMEAGENT_REFRESH_SECURE` to `True` for HTTPS deployments. Cross-site HTTPS deployments must also set `PRIMEAGENT_REFRESH_SAME_SITE=none`.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_ACCESS_SECURE` | Boolean | `False` | When `true`, the `access_token_lf` cookie is sent only over HTTPS. Recommended `true` for any HTTPS deployment. |
| `PRIMEAGENT_ACCESS_HTTPONLY` | Boolean | `True` | When `true`, the `access_token_lf` cookie is not readable by JavaScript. Set to `false` only if a client must read this cookie in JavaScript. |
| `PRIMEAGENT_ACCESS_SAME_SITE` | String | `lax` | The `SameSite` attribute of the access-token cookie (`lax`, `strict`, or `none`). |
| `PRIMEAGENT_REFRESH_SECURE` | Boolean | `False` | When `true`, the `refresh_token_lf` cookie is sent only over HTTPS. Set this to `true` for any HTTPS deployment. |
| `PRIMEAGENT_REFRESH_HTTPONLY` | Boolean | `True` | When `true`, the `refresh_token_lf` cookie is not readable by JavaScript. |
| `PRIMEAGENT_REFRESH_SAME_SITE` | String | `lax` | The `SameSite` attribute of the refresh-token cookie (`lax`, `strict`, or `none`). |
| `PRIMEAGENT_COOKIE_DOMAIN` | String | Not set | Domain attribute for the access and refresh cookies. Leave unset for host-only cookies. Set to a parent domain, such as `.example.com`, when the frontend and API are on different subdomains. |

### Anonymous public-flow authorization

Anonymous public-flow links are direct-link capabilities, not discovery grants. Primeagent accepts a canonical `PUBLIC` authorization share and preserves existing links derived from `Flow.access_type=PUBLIC` or an A2A folder with `auth_type=none`. Public shares never appear in general flow or shared-with-me listings.

A canonical `PUBLIC` share takes precedence over both compatibility grants. For flows, the shares API accepts only `permission_level=execute` at `PUBLIC` scope; execution includes the scrubbed direct-link read needed to load the playground. The API rejects `read`, `write`, and `admin` because there is no read-only, writable, or administrative anonymous flow surface. Deleting the share row removes the canonical grant and any still-set legacy setting becomes the effective grant again, so revoke access entirely by clearing the legacy setting as well.

An anonymous link grants only resource read and flow execution. It never grants create, write, delete, deploy, or administration actions, and callers cannot submit flow data or component tweaks. Public execution uses a stable non-user principal, so owner credentials, variables, files, and knowledge bases are unavailable unless a dependency has its own public authorization path. Errors are sanitized, and A2A HITL resumes recheck the current grant. Revocation blocks subsequent starts and resumes; it does not terminate work that is already running.

When `PRIMEAGENT_AUTHZ_ENABLED=true`, anonymous access also requires an authorization plugin that opts into public principals, maps request hosts through a deployment-owned allowlist, resolves a tenant from that mapping and server-derived domain context, and allows the action. The OSS public-principal plugin seam defaults to deny and never performs cross-tenant discovery. Plugins must not treat the raw `Host` header as a trusted tenant identity.

For A2A, `auth_type=none` applies this contract to both the direct agent card and execution routes. API-key and OAuth agent cards remain anonymously readable by direct link for A2A protocol discovery, but their JSON-RPC execution routes retain owner-key admission and owner execution.

### PRIMEAGENT_RATE_LIMIT_* {#login-rate-limiting}

The following environment variables configure IP-based rate limiting to protect against brute-force attacks on the `/login` endpoint and abuse of public flow endpoints.
When the limit is exceeded, Primeagent returns HTTP 429 with a `Retry-After: 60` header.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_RATE_LIMIT_ENABLED` | Boolean | `True` | Enable rate limiting on the `/login` and `/api/v2/workflows/public` endpoints. Set to False to disable those limits (not recommended in production). |
| `PRIMEAGENT_RATE_LIMIT_PER_MINUTE` | Integer | `5` | Maximum number of login attempts allowed per minute from a single IP address. |
| `PRIMEAGENT_RATE_LIMIT_STORAGE_URI` | String | `memory://` | Storage backend for rate limit counters. Use `memory://` for single-server deployments or `redis://host:port` for multi-server deployments where the limit should be shared across instances. |
| `PRIMEAGENT_RATE_LIMIT_TRUST_PROXY` | Boolean | `False` | When `true`, Primeagent reads the client IP from the rightmost `X-Forwarded-For` header entry instead of the direct connection IP. Enable only when Primeagent is behind a trusted reverse proxy or load balancer. Do not enable if users can reach Primeagent directly, as this allows header spoofing. |
| `PRIMEAGENT_PUBLIC_FLOW_RATE_LIMIT_PER_MINUTE` | Integer | `20` | Maximum number of unauthenticated public-flow runs allowed per minute from a single IP address. Public flows consume resources under an isolated anonymous principal, so they are rate-limited separately from the `/login` endpoint. |

### PRIMEAGENT_SSRF_* and PRIMEAGENT_CONNECTOR_SSRF_* {#ssrf-protection}

The following environment variables configure Server-Side Request Forgery (SSRF) protection for the [**API Request** component](/api-request) and for connector components that take a tenant-controlled host or URL.
SSRF protection prevents requests to internal or private network resources, such as private IP ranges, loopback addresses, and cloud metadata endpoints.

In a shared server where users you do not fully trust can build flows, set `PRIMEAGENT_CONNECTOR_SSRF_VALIDATION_ENABLED=true`, `PRIMEAGENT_SSRF_PROTECTION_ENABLED=true`, and `PRIMEAGENT_CONNECTOR_SSRF_ALLOW_LOOPBACK=false`, and then allowlist your own internal hosts with `PRIMEAGENT_SSRF_ALLOWED_HOSTS`.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_SSRF_PROTECTION_ENABLED` | Boolean | `True` | Enable SSRF protection for the **API Request** component. When enabled, the component blocks requests to private IP addresses. When disabled, requests are not blocked. |
| `PRIMEAGENT_SSRF_ALLOWED_HOSTS` | List[String] | Not set | A comma-separated list of allowed hosts, IP addresses, or CIDR ranges that can bypass SSRF protection checks. For example: `192.168.1.0/24,10.0.0.5,*.internal.company.local`.|
| `PRIMEAGENT_CONNECTOR_SSRF_VALIDATION_ENABLED` | Boolean | `True` | Apply SSRF host validation to connector components that take a tenant-controlled host or URL. Uses `PRIMEAGENT_SSRF_PROTECTION_ENABLED` and `PRIMEAGENT_SSRF_ALLOWED_HOSTS` for the host policy. Set to `false`, or allowlist specific hosts, only when a trusted single-tenant deployment intentionally connects to private-network services. |
| `PRIMEAGENT_CONNECTOR_SSRF_ALLOW_LOOPBACK` | Boolean | `True` | When connector SSRF validation is enabled, allow literal loopback hosts (`localhost`, `127.0.0.0/8`, `::1`) so local Ollama, LM Studio, and similar services keep working. Multi-tenant deployments where a tenant must not reach the server's loopback should set this to `false`. |

### Component hardening for untrusted users {#multi-tenant-component-hardening}

Use these variables when users who can build or run flows on your server should not get host-level code execution, arbitrary file reads, or  MCP mounts.

For more information, see [Docker image defaults](/deployment-docker#docker-image-security-defaults).

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_BLOCK_CODE_INTERPRETER_COMPONENTS` | Boolean | `False` | When `true`, blocks execution of any flow containing a built-in arbitrary-code-execution component, including the [**Python Interpreter**](/python-interpreter), Python REPL/Code tools, [**Smart Transform**](/smart-transform), [**CSV Agent**](/bundles-langchain#csv-agent), and code-running agents such as [**CodeAct**](/bundles-codeagents#codeact-agent-smolagents), [**CUGA**](/bundles-cuga), and [**OpenDsStar**](/bundles-codeagents#opendstar-agent). |
| `PRIMEAGENT_RESTRICT_LOCAL_FILE_ACCESS` | Boolean | `False` | When `true`, built-in file-reading components, including the [**File**](/read-file), [**Directory**](/legacy-core-components#legacy-data-components), [**JSON/CSV-to-Data**](/legacy-core-components#legacy-data-components), and the [**CSV Agent**](/bundles-langchain#csv-agent), [**JSON Agent**](/bundles-langchain#legacy-langchain-components), and [**OpenAPI Agent**](/bundles-langchain#openapi-agent) can only read and write paths inside the [`PRIMEAGENT_CONFIG_DIR`](/memory) storage directory. This also blocks `sqlite` and `duckdb` dialects in the [**SQL Database**](/sql-database) components and local-filesystem Git clones. |
| `PRIMEAGENT_MCP_SERVER_DOCKER_HARDENING` | Boolean | `False` | When `true`, applies a strict Docker-argument policy to MCP stdio servers that use the `docker` transport. Rejects host filesystem or device mounts, `host/another-container` namespaces, non-default networks, privilege flags, and sandbox-disabling `--security-opt` values. Forms such as `--network none` / `bridge` and `--security-opt no-new-privileges` remain allowed. |
| `PRIMEAGENT_TWEAKS_POLICY` | String | `permissive` | Which component fields a run request may set through `tweaks`. For more information, see [Restrict API tweaks](./deployment-tweaks-policy). |

Enable these flags when untrusted users can build flows on this server.

The `PRIMEAGENT_ALLOW_CUSTOM_COMPONENTS` and `PRIMEAGENT_BLOCK_CODE_INTERPRETER_COMPONENTS` flags support two deployment modes.
`PRIMEAGENT_ALLOW_CUSTOM_COMPONENTS=false` blocks user-authored component code and registered built-in code-execution components at runtime. Set `PRIMEAGENT_BLOCK_CODE_INTERPRETER_COMPONENTS=true` independently when custom components should remain enabled but built-in code execution should be disabled.

To enable these flags, set the following:

* `PRIMEAGENT_ALLOW_CUSTOM_COMPONENTS=false`: blocks user-authored component code and registered built-in code-execution components. See [Block custom components](/deployment-block-custom-components).
* `PRIMEAGENT_BLOCK_CODE_INTERPRETER_COMPONENTS=true`: blocks built-in code-execution components.
* `PRIMEAGENT_RESTRICT_LOCAL_FILE_ACCESS=true`: confines built-in file access to the upload sandbox.
* `PRIMEAGENT_MCP_SERVER_DOCKER_HARDENING=true`: tightens Docker MCP server arguments.
* `PRIMEAGENT_TWEAKS_POLICY=declared` or `off`: limits which component fields an API caller can override at run time. See [Restrict API tweaks](./deployment-tweaks-policy).

To block named built-in components, starter templates, model providers, or models across the install, use the [catalog and model policy APIs](./api-governance-policy).

Pair these settings with the [SSRF settings](#ssrf-protection) to reduce common escape hatches.

These settings **do not** provide full user isolation. For more information, see [Security](/security).

:::tip
Do not enable a shared tracer when users are untrusted. Instead, use [built-in local tracing](/traces).
External tracing integrations such as Langfuse and Arize are _process-wide_, not per user, so on a shared server, every user's flow inputs and outputs will go to the same tracing project.
:::

### PRIMEAGENT_WEBHOOK_AUTH_ENABLE {#primeagent-webhook-auth-enable}

This variable controls whether API key authentication is required for webhook endpoints.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `PRIMEAGENT_WEBHOOK_AUTH_ENABLE` | Boolean | `True` | When `True`, webhook endpoints require API key authentication and validate that the authenticated user owns the flow being executed. When `False`, no Primeagent API key is required and all requests to the webhook endpoint are treated as being sent by the flow owner. |

By default, webhooks require API key authentication with `PRIMEAGENT_WEBHOOK_AUTH_ENABLE=True`.

To allow webhooks to run without authentication (not recommended; use only in trusted environments), in your Primeagent `.env` file, set `PRIMEAGENT_WEBHOOK_AUTH_ENABLE=False`.

When webhook authentication is enabled, you must provide a Primeagent API key with each webhook request as an HTTP header or query parameter. For more information, see [Require authentication for webhooks](/webhook#require-authentication-for-webhooks).

## Configure JWT token signing {#configure-jwt-token-signing}

Primeagent issues short-lived JSON Web Tokens (JWTs) when a user logs in. The default HS256 algorithm works for most deployments. Switch to RS256 or RS512 for production deployments that require asymmetric keys or need to share the public key with other services.

<details closed>
<summary>About the JWT structure and contents</summary>

When a user logs in at the `/api/v1/login` endpoint, Primeagent validates the credentials and creates a JWT containing the user's identity and expiration time. This token is then used for subsequent API requests instead of sending credentials with each request.

A JWT consists of three parts separated by dots (`.`):

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

* The header contains the token type and signing algorithm.
* The payload contains _claims_ — token data for user information and expiration time.
* The signature ensures the token hasn't been tampered with.

Each part of the JWT is Base64URL-encoded. You can paste this example JWT to decode the actual JSON data at [jwt.io](https://jwt.io/).

</details>

The following environment variables control JWT signing. `PRIMEAGENT_SECRET_KEY` is also used for data encryption and is documented separately in [`PRIMEAGENT_SECRET_KEY`](#primeagent-secret-key).

| Variable | Description | Default |
|---|---|---|
| `PRIMEAGENT_ALGORITHM` | JWT signing algorithm: `HS256`, `RS256`, or `RS512` | `HS256` |
| `PRIMEAGENT_PRIVATE_KEY` | RSA private key for RS256/RS512 signing | Auto-generated |
| `PRIMEAGENT_PUBLIC_KEY` | RSA public key for RS256/RS512 verification | Derived from private key |
| `PRIMEAGENT_ACCESS_TOKEN_EXPIRE_SECONDS` | Access token expiration time | `3600` (1 hour) |
| `PRIMEAGENT_REFRESH_TOKEN_EXPIRE_SECONDS` | Refresh token expiration time | `604800` (7 days) |

### HS256 (default)

HS256 is the default JWT algorithm, suitable for single-server deployments.
Primeagent automatically generates and persists a secret key via `PRIMEAGENT_SECRET_KEY`.
No configuration is necessary beyond what is already covered in the [`PRIMEAGENT_SECRET_KEY`](#primeagent-secret-key) section above.

To explicitly set the algorithm in your `.env`:

```bash
PRIMEAGENT_ALGORITHM=HS256
PRIMEAGENT_SECRET_KEY="your-custom-secret-key"
```

### RS256

RS256 uses an RSA private/public key pair. The private key signs tokens; the public key verifies them. Use RS256 for production deployments or multi-instance setups where you want to share the public key with other services.

To automatically generate a key pair, set the algorithm and Primeagent creates and persists the keys in [`PRIMEAGENT_CONFIG_DIR`](/logging) on startup:

```bash
PRIMEAGENT_ALGORITHM=RS256
```

To supply your own private key (public key is derived automatically):

```bash
PRIMEAGENT_ALGORITHM=RS256
PRIMEAGENT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEF...
-----END PRIVATE KEY-----"
```

To supply a full key pair:

```bash
PRIMEAGENT_ALGORITHM=RS256
PRIMEAGENT_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----
MIIEvgIBADANBgkqhkiG9w0BAQEF...
-----END PRIVATE KEY-----"
PRIMEAGENT_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOC...
-----END PUBLIC KEY-----"
```

To generate an RSA key pair manually:

1. Generate a 2048-bit private key:
   ```bash
   openssl genrsa -out private_key.pem 2048
   ```

2. Extract the public key:
   ```bash
   openssl rsa -in private_key.pem -pubout -out public_key.pem
   ```

### RS512

RS512 uses the same RSA key format as RS256 but with SHA-512 hashing for greater cryptographic strength. Key generation and configuration follow the same pattern as RS256 — substitute `RS512` for `RS256` in all the examples above.

### Configure Docker and Kubernetes deployments

**Docker with HS256** — for single-server or development deployments:

```yaml
services:
  primeagent:
    image: khulnasoft/primeagent:latest
    environment:
      - PRIMEAGENT_ALGORITHM=HS256
      - PRIMEAGENT_SECRET_KEY=${PRIMEAGENT_SECRET_KEY}
    volumes:
      - primeagent_data:/app/primeagent
volumes:
  primeagent_data:
```

**Docker with RS256** — auto-generated keys (persisted in the volume):

```yaml
services:
  primeagent:
    image: khulnasoft/primeagent:latest
    environment:
      - PRIMEAGENT_ALGORITHM=RS256
    volumes:
      - primeagent_data:/app/primeagent
volumes:
  primeagent_data:
```

**Docker with RS256** — mount an existing key pair:

```yaml
services:
  primeagent:
    image: khulnasoft/primeagent:latest
    environment:
      - PRIMEAGENT_ALGORITHM=RS256
    volumes:
      - ./keys/private_key.pem:/app/primeagent/private_key.pem:ro
      - ./keys/public_key.pem:/app/primeagent/public_key.pem:ro
      - primeagent_data:/app/primeagent
volumes:
  primeagent_data:
```

**Kubernetes with RS256** — store keys as Secrets:

```yaml
# jwt-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: primeagent-jwt-keys
type: Opaque
stringData:
  algorithm: "RS256"
  private-key: |
    -----BEGIN PRIVATE KEY-----
    MIIEvgIBADANBgkqhkiG9w0BAQEF...
    -----END PRIVATE KEY-----
  public-key: |
    -----BEGIN PUBLIC KEY-----
    MIIBIjANBgkqhkiG9w0BAQEFAAOC...
    -----END PUBLIC KEY-----
---
# primeagent-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: primeagent
spec:
  template:
    spec:
      containers:
        - name: primeagent
          image: khulnasoft/primeagent:latest
          env:
            - name: PRIMEAGENT_ALGORITHM
              valueFrom:
                secretKeyRef:
                  name: primeagent-jwt-keys
                  key: algorithm
            - name: PRIMEAGENT_PRIVATE_KEY
              valueFrom:
                secretKeyRef:
                  name: primeagent-jwt-keys
                  key: private-key
            - name: PRIMEAGENT_PUBLIC_KEY
              valueFrom:
                secretKeyRef:
                  name: primeagent-jwt-keys
                  key: public-key
```

### Configure token expiration

Access tokens authenticate API requests and typically expire within 15 minutes to 1 hour.
Refresh tokens obtain new access tokens without requiring the user to log in again and typically expire within 7 to 30 days.
When an access token expires, the client can use the refresh token to get a new one from `/api/v1/refresh`.

```bash
PRIMEAGENT_ACCESS_TOKEN_EXPIRE_SECONDS=3600    # 1 hour
PRIMEAGENT_REFRESH_TOKEN_EXPIRE_SECONDS=604800 # 7 days
```

## Start a Primeagent server with authentication enabled {#start-a-primeagent-server-with-authentication-enabled}

This section shows you how to use the [authentication environment variables](/api-keys-and-authentication#authentication-environment-variables) to deploy a Primeagent server with authentication enabled.
This involves disabling automatic login, setting superuser credentials, and generating a secret encryption key.

This configuration is recommended for any deployment where Primeagent is exposed to a shared or public network, or where multiple users access the same Primeagent server.

:::tip Docker images
Official Primeagent Docker images already set `PRIMEAGENT_AUTO_LOGIN=false`.
You still must set `PRIMEAGENT_SUPERUSER_PASSWORD` (and optionally `PRIMEAGENT_SUPERUSER`) before the container can start.
For more information, see [Docker image defaults](/deployment-docker#docker-image-security-defaults).
:::

With authentication enabled, all users must sign in to the visual editor with valid credentials, and API requests require authentication with a Primeagent API key.
Sign in as a superuser to [create a Primeagent API key](#create-a-primeagent-api-key) with superuser privileges.
User management is through the [Users API](/api-users), not the visual editor.

### Start the Primeagent server

1. Create a `.env` file with the following variables:

    ```text
    PRIMEAGENT_AUTO_LOGIN=False
    PRIMEAGENT_SUPERUSER=
    PRIMEAGENT_SUPERUSER_PASSWORD=
    PRIMEAGENT_SECRET_KEY=
    PRIMEAGENT_NEW_USER_IS_ACTIVE=False
    PRIMEAGENT_ENABLE_SIGNUP=False
    PRIMEAGENT_ENABLE_SUPERUSER_CLI=False
    ```

    Your `.env` file can have other environment variables.
    This example focuses on authentication variables.

    `PRIMEAGENT_ENABLE_SIGNUP=False` restricts account creation to superusers.
    `PRIMEAGENT_NEW_USER_IS_ACTIVE=False` keeps new accounts inactive until you activate them with the Users API.

2. Set `PRIMEAGENT_SUPERUSER_PASSWORD` to your desired superuser password. Optionally set `PRIMEAGENT_SUPERUSER` to override the default `primeagent` username.

    For a one-time test, you can use basic credentials like `administrator` and `password`.
    Strong, securely-stored credentials are recommended in genuine development and production environments.

3. Recommended: Generate and set a `PRIMEAGENT_SECRET_KEY` for encrypting sensitive data.

    If you don't set a secret key, Primeagent generates one automatically, but this isn't recommended for production environments.

    For instructions on generating and setting a secret key, see [`PRIMEAGENT_SECRET_KEY`](#primeagent-secret-key).

4. Save your `.env` file with the populated variables. For example:

    ```text
    PRIMEAGENT_AUTO_LOGIN=False
    PRIMEAGENT_SUPERUSER=administrator
    PRIMEAGENT_SUPERUSER_PASSWORD=securepassword
    PRIMEAGENT_SECRET_KEY=dBuu...2kM2_fb
    PRIMEAGENT_NEW_USER_IS_ACTIVE=False
    PRIMEAGENT_ENABLE_SIGNUP=False
    PRIMEAGENT_ENABLE_SUPERUSER_CLI=False
    ```

5. Start Primeagent with the configuration from your `.env` file:

    ```text
    uv run primeagent run --env-file .env
    ```

    Starting Primeagent with this `.env` file creates or uses the configured superuser.
    If `PRIMEAGENT_SUPERUSER_PASSWORD` isn't set, startup fails instead of creating a default password.

6. Verify the server is running. The default location is `http://localhost:7860`.

Next, add users with the Users API so they can collaborate on flows.

### Manage users as an administrator

As of Primeagent 1.12, Primeagent OSS has no **Admin Page** in the visual editor.
Superusers add, activate, list, and delete users, set **Superuser**, and set other users' passwords with `PATCH /api/v1/users/{id}`. For more information, see [Users endpoints](/api-users).

1. To complete your first-time login as a superuser, navigate to `http://localhost:7860/login`.

    If you aren't using the default location, replace `localhost:7860` with your server's address.

2. Log in with the password you set in `PRIMEAGENT_SUPERUSER_PASSWORD` and the username from `PRIMEAGENT_SUPERUSER`.
    If you did not set `PRIMEAGENT_SUPERUSER`, the username is `primeagent`.

3. [Create a Primeagent API key](#create-a-primeagent-api-key) while signed in as the superuser.
    User-management requests require a Primeagent API key in the `x-api-key` header.

4. Create a user:

    <Tabs groupId="users-api">
    <TabItem value="Python" label="Python" default>

    ```python
    import os

    import requests

    base = os.environ["PRIMEAGENT_URL"]
    headers = {
        "Content-Type": "application/json",
        "x-api-key": os.environ["PRIMEAGENT_API_KEY"],
    }
    payload = {
        "username": "newuser",
        "password": "securepassword123",
    }

    response = requests.post(f"{base}/api/v1/users/", headers=headers, json=payload, timeout=30)
    response.raise_for_status()
    print(response.json())
    ```

    </TabItem>
    <TabItem value="typescript" label="TypeScript">

    ```typescript

    const response = await fetch(url, {
      method: "POST",

      },

        username: "newuser",
        password: "securepassword123",
      }),
    });

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);

    ```

    </TabItem>
    <TabItem value="curl" label="curl">

    ```bash
    curl -X POST \
      "$PRIMEAGENT_URL/api/v1/users/" \
      -H "Content-Type: application/json" \

      -d '{
        "username": "newuser",
        "password": "securepassword123"
      }'
    ```

    </TabItem>
    </Tabs>

    The response includes the user's `id`.
    New accounts are inactive when `PRIMEAGENT_NEW_USER_IS_ACTIVE=False` (the default, and the value in the `.env` example above).

5. Activate the account so the user can sign in.
    Replace `USER_ID` with the `id` from the create response:

    <Tabs groupId="users-api">
    <TabItem value="Python" label="Python" default>

    ```python
    import os

    import requests

    base = os.environ["PRIMEAGENT_URL"]
    user_id = "USER_ID"
    headers = {
        "Content-Type": "application/json",
        "x-api-key": os.environ["PRIMEAGENT_API_KEY"],
    }
    payload = {"is_active": True}

    response = requests.patch(
        f"{base}/api/v1/users/{user_id}", headers=headers, json=payload, timeout=30
    )
    response.raise_for_status()
    print(response.json())
    ```

    </TabItem>
    <TabItem value="typescript" label="TypeScript">

    ```typescript
    const userId = "USER_ID";
    const url = `${process.env.PRIMEAGENT_URL}/api/v1/users/${userId}`;

    const response = await fetch(url, {
      method: "PATCH",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": process.env.PRIMEAGENT_API_KEY!,
      },
      body: JSON.stringify({ is_active: true }),
    });

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    console.log(await response.json());
    ```

    </TabItem>
    <TabItem value="curl" label="curl">

    ```bash
    curl -X PATCH \
      "$PRIMEAGENT_URL/api/v1/users/USER_ID" \
      -H "Content-Type: application/json" \
      -H "x-api-key: $PRIMEAGENT_API_KEY" \
      -d '{
        "is_active": true
      }'
    ```

    </TabItem>
    </Tabs>

    To grant administrative privileges, include `"is_superuser": true` in the same request.
    To reset another user's password, `PATCH /api/v1/users/{id}` with `"password": "<new password>"`. That path does not require the current password. `PATCH /api/v1/users/{id}/reset-password` is self-service: it must be called as that user and requires `current_password`. See [Update user](./api-users#update-user).
    To list, deactivate, or delete a user, see [Users endpoints](/api-users).

6. Send the username and password to the user.
    The superuser sets the initial password when creating the account.

7. To test the new user's access, sign out of Primeagent, and then sign in at `/login` with the new user's credentials.
    A non-superuser can use the visual editor and cannot call the Users API to manage other accounts.
