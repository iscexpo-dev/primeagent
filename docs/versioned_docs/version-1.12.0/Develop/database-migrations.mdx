Primeagent stores application data such as flows, users, and API keys in a SQL database.

When you upgrade Primeagent or connect to a new empty database, Primeagent must keep the database schema aligned with the application models.

By default, the Primeagent database uses [SQLite](https://www.sqlite.org/docs.html), and uses [Alembic](https://alembic.sqlalchemy.org/) for SQL database migrations.

This page explains when migrations run and how to run and repair migrations safely.

## Default migrations behavior and triggers

Most Primeagent users never need to run a database migration.
When you start Primeagent, or restart a container after upgrading the Primeagent image, pending Alembic migrations run as part of database initialization.

Primeagent includes [Alembic revision scripts](https://github.com/khulnasoft-bot/primeagent/tree/main/src/backend/base/primeagent/alembic) with the package.
On startup, Primeagent connects to the database at [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) or the default `primeagent.db` file, ensures the required tables exist, checks the database schema against the current models, and then applies any pending Alembic upgrades to bring the schema to its `head` revision.

Alembic records the applied revision in the `alembic_version` table.

Other events that trigger Alembic checks are a first Primeagent startup against a new SQLite file or empty PostgreSQL database, upgrading to a Primeagent version that includes new Alembic revisions, or pointing [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) at an empty database.

## Upgrade Primeagent safely

To upgrade Primeagent or change the database URL in a deployment that already has data, you may need a database migration.
To migrate your database, do the following:

1. Stop Primeagent.
2. Back up the database.

    If you're using SQLite, copy the `primeagent.db` file.
    The default path depends on your install method and whether `PRIMEAGENT_SAVE_DB_IN_CONFIG_DIR` is set.
    For more information, see [Memory management options](/memory#storage-options-and-paths).

    If you're using PostgreSQL, make a logical backup with `pg_dump`, or use your database provider's snapshot.
    For more information, see [enterprise backup guidance](/enterprise-database-guide).

3. Export any flows you want to save as JSON. For more information, see [Import and export flows](/concepts-flows-import).
4. Upgrade the Primeagent package or container image to the latest version, keeping the same [`PRIMEAGENT_DATABASE_URL`](/memory#configure-external-memory) or the same SQLite path.

    ```bash
    uv pip install primeagent -U
    ```

5. Start a **single** Primeagent instance, so database migrations run without concurrent database writes.
6. Confirm that startup succeeds.
7. If startup reports a schema mismatch, run `primeagent migration` to inspect the problem and restore from backup if needed.
   For more information, see [`primeagent migration` CLI](/configuration-cli#primeagent-migration).

## Switch from SQLite to PostgreSQL

Changing `PRIMEAGENT_DATABASE_URL` from SQLite to PostgreSQL does **not** copy existing SQLite data into PostgreSQL.
Primeagent initializes and migrates the new database schema, and your previous SQLite file remains where it was.

There is no built-in SQLite-to-PostgreSQL data migrator.
Primeagent creates a new PostgreSQL schema, and then you can restore application data you saved.

To migrate your flows while switching from SQLite to PostgreSQL, do the following:

1. [Export flows](/concepts-flows-import), and note any [global variables](/configuration-global-variables) or credentials.
2. Provision PostgreSQL 15+ and set `PRIMEAGENT_DATABASE_URL` as described in [Configure an external PostgreSQL database](/configuration-custom-database).
3. If required, install PostgreSQL driver extras, for example `uv pip install "primeagent[postgresql]"`.
4. Start Primeagent. The new PostgreSQL schema is created.
5. Import the exported flows and recreate secrets or variables as needed.

## Migration logging

Alembic output is written to a log file by default at `alembic/alembic.log` under the Primeagent config directory (`PRIMEAGENT_CONFIG_DIR`).
Relative `PRIMEAGENT_ALEMBIC_LOG_FILE` values are also resolved against that config directory.
In read-only or hardened containers, that path may not be writable, and Primeagent will fall back to `stdout` and continue the migration.

## Migration environment variables

| Variable | Purpose |
|----------|---------|
| `PRIMEAGENT_ALEMBIC_LOG_TO_STDOUT` | Set to `true` to send Alembic migration output to `stdout`. |
| `PRIMEAGENT_ALEMBIC_LOG_FILE` | Absolute or relative path for the Alembic log file when not logging to `stdout`. Relative paths resolve under the Primeagent config directory. |
| `PRIMEAGENT_MIGRATION_LOCK_TIMEOUT_S` | Seconds to wait for the PostgreSQL migration advisory lock. Default: `300`. |
| `PRIMEAGENT_MIGRATION_LOCK_NAMESPACE` | Optional namespace for the Alembic PostgreSQL advisory lock. The default lock key coordinates instances that share a database. Set this variable to isolate different Primeagent deployments that share one PostgreSQL server. Use the same value on every instance in that deployment. |
